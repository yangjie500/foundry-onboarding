# SQS onboarding integration contract

## Status and ownership

This document defines the proposed version 1 message contract for onboarding
requests received from Amazon SQS. The development queue will be provisioned by
this project to simulate the integration. The production queue and its dead-letter
queue are owned and operated by another team; this project will only integrate
its ingress Lambda with that queue.

The schema is implemented locally so development can proceed, but the external
queue-owning team must approve the contract and the open integration details
before production integration.

## Message body

The SQS message body is a UTF-8 JSON object. It is not an entire SQS event and
must not be wrapped in another application-specific envelope:

```json
{
  "schema_version": "1.0",
  "request_id": "f084a40c-2d45-4bc9-96b2-d650bb746413",
  "action": "onboard_user",
  "payload": {
    "username": "jane.smith",
    "name": "Jane Smith",
    "email": "jane.smith@example.com",
    "external": false
  }
}
```

The contract is implemented by `SqsOnboardingMessage` in
`foundry_onboarding.contracts.sqs_onboarding`. The representative fixture is
`events/sqs/onboarding/valid.json`.

## Fields and validation

| Field | Requirement |
| --- | --- |
| `schema_version` | Required and exactly `1.0` |
| `request_id` | Required UUID generated by the producer |
| `action` | Required and exactly `onboard_user` |
| `payload.username` | Required GitLab-compatible username, 2-255 characters |
| `payload.name` | Required, 1-255 characters after surrounding whitespace is removed |
| `payload.email` | Required valid email address, at most 254 characters |
| `payload.external` | Required JSON boolean |

Unknown top-level and payload fields are rejected. String representations of
booleans are rejected. Credentials, access tokens, passwords, and secrets must
never be included in the message body or message attributes.

No SQS message attribute is required for business processing. AWS-generated SQS
record metadata is transport metadata and is not part of this contract.

## Contract boundary

The external message contract is deliberately separate from
`GenericWorkflowInput`, even though their current onboarding fields are the
same. After validation, the ingress component explicitly converts the external
message into the internal workflow contract. This allows either side of the
integration to evolve without silently changing the other.

The SQS contract accepts only `onboard_user`; it does not expose the temporary
internal `echo` workflow action.

## Delivery and idempotency rules

SQS delivery is treated as at-least-once, so duplicate deliveries are expected.
The producer must generate `request_id`. A request ID identifies one immutable
logical request: the producer must never reuse it with a different payload.

The planned ingress service will use the request ID to derive a deterministic
Step Functions execution identity. Receiving the same request again can then be
treated as an acknowledged duplicate. Detecting the same request ID with a
different payload requires a persistent request fingerprint and is not part of
the initial implementation, so the immutable-request rule is a required
producer guarantee.

Personal information such as name and email is business input, not a credential,
but it remains sensitive. Message bodies must not be written to application logs.

## Failure boundary

The implemented ingress handler applies these failure boundaries:

- malformed JSON and contract validation failures will be rejected;
- temporary failures to start the workflow will be retried through SQS;
- a message will be acknowledged after the workflow is successfully started or
  identified as an already-started duplicate; and
- failures after the workflow starts belong to Step Functions monitoring and do
  not return the original message to SQS.

The final retry and dead-letter behavior depends on the queue configuration
agreed with its owner.

The handler returns failed record identifiers using Lambda's partial batch
response format, so one rejected record does not cause successfully started
records in the same Standard queue batch to be delivered again. FIFO ordering
behavior is not yet implemented because the external queue type remains open.

The ingress application code has an isolated dependency group, hashed
requirements export, and guarded Lambda asset build target. Its package has
been built and import-verified with Docker. It is not yet defined as a CDK Lambda
or connected to an SQS event source. The future event-source mapping must enable
`ReportBatchItemFailures` for the returned record failures to affect SQS
delivery.

## External-team decisions still required

Before production integration, confirm:

1. Whether the queue is Standard or FIFO.
2. The AWS account, Region, queue ARN, and queue URL for each environment.
3. Approval of this JSON schema and the immutable `request_id` rule.
4. Whether messages arrive directly or through SNS or EventBridge. If SNS is
   involved, confirm whether raw message delivery is enabled.
5. Whether the queue uses an AWS-owned or customer-managed KMS key.
6. Queue policy ownership and the permissions granted to the ingress Lambda.
7. Visibility timeout, retention period, maximum receive count, and redrive
   policy.
8. Dead-letter queue ownership, alerting, investigation, and replay procedures.
9. Which team creates and manages the Lambda event-source mapping.
10. Personal-data retention and access requirements.

Development defaults must simulate these decisions once they are known. This
project must not provision or replace the production queue.

## Development simulation infrastructure

The development stack provisions a Standard input queue and dead-letter queue
owned by this project:

```text
foundry-dev-onboarding
foundry-dev-onboarding-dlq
```

Both queues use SQS-managed server-side encryption and resource policies that
deny non-TLS requests. The input queue has a 180-second visibility timeout,
four-day retention, and a redrive policy that moves a message to the DLQ after
five failed receives. The DLQ retains messages for fourteen days.

The queues use a destroy removal policy because they contain development
simulation data. Destroying the development stack deletes both queues and any
messages they contain. Staging and production configurations explicitly disable
development queue provisioning; the external production queue remains owned by
the other team.

The stack exports the input and dead-letter queue URLs and ARNs. The ingress
Lambda and SQS event-source mapping are not yet defined, so messages sent before
that connection is implemented remain waiting in the input queue.
